# 0001. Выбор модели процесса разработки

## Статус

Принято

## Контекст

BioPrep — конвейер первичной обработки изображений из четырёх модулей, разработанных в НИР по теме магистерской диссертации. Исполнитель один; научный руководитель выступает заказчиком и ревьюером; общение в основном дистанционное. Срок задан графиком подготовки диссертации.

Анализ в лабораторной работе № 1 показал, что модули сильно различаются по профилю:

| Модуль | Неопределённость требований | Критичность | Частота изменений | Аудит |
|---|---|---|---|---|
| М1 PCNN+PSO (шумоподавление) | средняя | высокая | высокая | средний |
| М2 ACO (границы) | высокая | средняя | высокая | средний |
| М3 ГА (сегментация, критерий Капура) | низкая | средняя | низкая | средний |
| М4 метрики и протокол экспериментов | низкая | высокая | низкая | высокий |

Сводная матрица применимости (0/1/2): Waterfall/V-model — 1, 0, 2, 2; Incremental — 1, 1, 2, 1; Spiral — 2, 2, 1, 1; Scrum — 1, 2, 1, 0 (по модулям М1–М4). Ни одна модель не подходит одинаково хорошо для всех модулей.

## Решение

Принят гибридный процесс «спираль + V-модель + итеративные спринты»:

1. **Рамка проекта — спиральная модель.** Виток — этап исследования: (1) НИР — прототипы и метрики (выполнен); (2) перенос в репозиторий, тесты, CI; (3) расширения (цветные изображения, ускорение ACO), финальные эксперименты; (4) оформление диссертации. В начале витка обновляется реестр рисков.
2. **М4 и М3 — V-модель.** Спецификация метрик и протокола пишется вместе с приёмочными и модульными тестами (эталон — scikit-image, ручной расчёт, полный перебор для K = 1–2). М4 выпускается замороженным базовым релизом до сравнительных экспериментов.
3. **М1 и М2 — двухнедельные итерации** (упрощённый Scrum: Product Owner — научный руководитель; обзор — встреча с руководителем). Исследовательские вопросы — ограниченные по времени спайки. Доска Kanban, WIP-лимит In Progress = 2.

Синхронизация релизов: trunk-based-интеграция через Pull Request, тег `v0.x` в конце каждого спринта, общий контракт модулей «(H, W) float32 [0, 1] → результат», проверяемый интеграционными тестами. Изменение М4 — мажорная версия, отдельный ADR и пересчёт всех результатов. Каждый эксперимент записывает хэш коммита, версию М4 и seed. `v1.0` — к предзащите.

## Последствия

**Плюсы**

- исследовательские риски М1/М2 снимаются прототипами на ранних витках, а не в конце;
- результаты, попадающие в диссертацию, опираются на верифицированную и замороженную подсистему оценки;
- модули меняются независимо благодаря контракту интерфейсов.

**Ограничения и обязательства**

- требуется дисциплина: ограничение витков по времени, Definition of Done с порогами метрик;
- в CI нужно поддерживать проверки бюджета времени (140 / 210 / 110 мс, конвейер ≤ 500 мс) и регрессию метрик (±0,1 дБ PSNR, ±0,005 SSIM);
- правило «1 approve» требует участия научного руководителя или преподавателя в ревью;
- изменение подсистемы оценки становится дорогим — это сознательная цена сопоставимости результатов.
