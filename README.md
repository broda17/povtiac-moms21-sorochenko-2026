# BioPrep — биоинспирированная первичная обработка изображений

Сквозной проект дисциплины «Проектирование и оценка качества программных систем» (ДГТУ, кафедра ПОВТиАС, группа МОМС21, 2026/27 уч. год).

## Описание

BioPrep — модульный конвейер первичной обработки полутоновых изображений на основе биоинспирированных алгоритмов. Шумоподавление выполняет импульсная нейронная сеть PCNN, параметры которой автоматически подбирает рой частиц (PSO); границы выделяет муравьиный алгоритм (ACO), а многоуровневую сегментацию по энтропии Капура — генетический алгоритм. Проект развивает результаты НИР по теме магистерской диссертации и переносит прототипы в воспроизводимую инженерную форму с тестами и CI.

| Модуль | Назначение | Бюджет времени (512×512) |
|---|---|---|
| М1 `bioprep.denoise` | шумоподавление PCNN + калибровка PSO | ≤ 140 мс |
| М2 `bioprep.edges` | карта границ ACO | ≤ 210 мс |
| М3 `bioprep.segmentation` | сегментация ГА (критерий Капура) + совмещение с картой границ | ≤ 110 мс |
| М4 `bioprep.metrics` | метрики PSNR, SSIM, F-мера, мера Пратта; протокол экспериментов | — |
| Конвейер `bioprep.pipeline` | сборка М1–М3 | ≤ 500 мс |

Нефункциональные требования: производительность (бюджеты выше), надёжность (воспроизводимость метрик при фиксированных seed), безопасность (валидация входных файлов, кэш калибровки только в JSON).

## Contributing

### Модель ветвления: Trunk-Based Development

Выбрана **Trunk-Based Development** с обязательным Pull Request в `main`:

- в проекте один разработчик и еженедельный ритм лабораторных работ — параллельная поддержка нескольких версий (главное преимущество GitFlow) не нужна;
- процесс проекта — итеративные спринты для исследовательских модулей (ADR 0001), поэтому интеграция должна быть частой, а ветки — короткоживущими (не более 1–2 дней);
- одна основная ветка упрощает CI/CD и будущие quality gates (неделя 17).

Версии фиксируются тегами `v0.x` в конце каждого спринта, а не отдельными release-ветками.

### Защита ветки `main`

- прямой push в `main` запрещён, изменения — только через Pull Request;
- перед мержем нужен минимум 1 approve другого участника;
- прохождение CI будет обязательным с недели 17.

### Именование веток

```
feature/<номер-issue>-<краткое-описание>   # новая функциональность
fix/<номер-issue>-<краткое-описание>       # исправление дефекта
docs/<номер-issue>-<краткое-описание>      # документация
chore/<номер-issue>-<краткое-описание>     # инфраструктура, CI
```

Пример: `feature/1-adr-process-model`.

### Сообщения коммитов

Формат Conventional Commits: `feat:`, `fix:`, `docs:`, `test:`, `ci:`, `chore:`, `refactor:`. В теле — ссылка на issue (`Refs #1`, `Closes #1`).

### Задачи и метки

- шаблоны issue: «Новая задача» и «Дефект»;
- метки трёх измерений: тип (`feature`, `bug`, `tech-debt`, `docs`), приоритет (`priority:high`, `priority:medium`, `priority:low`), неделя курса (`week-01` … `week-17`). Метки задаются в [`.github/labels.tsv`](.github/labels.tsv) и создаются workflow [`labels.yml`](.github/workflows/labels.yml);
- доска задач: Backlog → To Do → In Progress → In Review → Done, WIP-лимит колонки In Progress — 2.
